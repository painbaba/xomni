Troubleshooting

Real fixes for the issues that actually come up: slow free-model responses, Ollama port conflicts, firewall prompts, PowerShell parse failures, MCP servers that won't connect, and plugin slowdowns. If something feels dead, start with /models — most "is it broken?" questions are really "which provider is slow?".

Slow responses

XOMNI routes through a pool of 25 free models on a shared gateway. 2–26 s per response is normal for free-model latency — a 10–20 s single call on the slow provider is typical, and per-turn hook overhead adds well under 1 s on top. Before blaming anything else, check provider health live:

inside XOMNI
> /models            # live status + list of the 25 verified free models
> /models coding     # filter: fast | reasoning | coding | vision | frontier

If a provider shows unhealthy or erroring, the pool fails over to the next free model automatically. A long pause followed by a normal answer is the slow gateway, not a hang — wait it out or switch to a fast model.

API timeouts

A request_timeout_seconds of 25 s turns long-context calls on the slow gateway into hard failures that feel like the agent is dead. The host-level fix that landed after the 100x incident: keep it at 120 s or higher.

config.yaml
request_timeout_seconds: 120   # 25s caused timeout-death on slow gateways

Low timeouts amplify any per-turn plugin overhead into hard errors — if you raised one knob, raise this one too.

Ollama / LM Studio port conflicts

XOMNI's zero-install Ollama runtime serves on 127.0.0.1:11434; the local-models plugin also probes LM Studio on :1234/v1. If another Ollama instance is already answering, the start script exits cleanly (already serving). But a non-Ollama app holding the port blocks the bind entirely:

cmd.exe
C:\> netstat -ano | findstr 11434

Free the port (or stop the other app), or point the runtime elsewhere with OLLAMA_HOST — note the plugin still probes 127.0.0.1:11434/v1 by default, so changing the port means reconfiguring the probe too. Check what the plugin sees at any time with /localmodels status and /localmodels scan.

Firewall blocks

The first ollama serve may trigger a Windows Firewall prompt — allow it (localhost traffic is usually exempt). If local models never come up and you dismissed the prompt, re-run run.cmd and accept it.

PowerShell parse issues (BOM)

If you edit ollama/start-ollama.ps1, keep the UTF-8 BOM. Windows PowerShell 5.1 reads BOM-less files as ANSI, which mangles non-ASCII characters and breaks parsing — the shipped script carries the BOM for exactly this reason. Save with UTF-8 with BOM encoding, or the whole zero-install flow fails with cryptic parse errors.

MCP servers won't connect

After adding a server from the 311-server catalog, confirm it registered, then reload:

terminal
$ hermes mcp list   # does the server show up?
  • If it's missing from hermes mcp list, the add failed — re-run hermes mcp add <name> -- <install_command> and restart (or use /reload-mcp).
  • Windows npx gotcha: for npx-based servers use the cmd /c form in config.yaml — bare npx as the command doesn't resolve on Windows: mcp_servers.filesystem: {command: "cmd", args: ["/c", "npx", "-y", "@modelcontextprotocol/server-filesystem", "C:/path/to/allowed"]}.
  • Verify with a read-only tool call — ask the agent to list files in the allowed directory.

Plugin slowdowns (speed checks)

After the 100x incident, every plugin cold-imports in under 90 ms and steady-state hook overhead is ~1.9 ms/turn. Enforce both gates after any plugin change:

bash
$ python .bench/ci_gate.py               # full plugin sweep, 90 ms import limit
$ python .bench/ci_gate.py --limit-ms 120  # custom import ceiling

The root causes of the 100x were configuration, not any single plugin. Rules that prevent a repeat:

  • Never enable prompt-enhancer auto mode (allow_provider_override: true) — one extra LLM call per turn was the primary multiplier. Run enhancement as an explicit command instead.
  • Enable ≤ 5 plugins total; at most one may touch llm at all, and never inside a hook.
  • Grep for perf-contract violations: grep -rn 'ctx.llm' plugins/*/__init__.py — any hit inside a _on_* hook is a violation.
  • Per-event file I/O in hooks was a measured 90–107 ms per event; now batched to ≤ 1 flush/30 s. If you write hooks, keep them deterministic and in-memory.
  • Target: < 1 s/turn total overhead. Current steady state is ~1.9 ms/turn.

Ollama runtime issues

  • Slow pull — qwen2.5:3b is ~1.9 GB and registry throttling can slow it. Re-run /ollama pull qwen2.5:3b to resume; pulls happen only on first run.
  • "did not answer in 90 s" warning — serve may still come up late; check with /ollama status.
  • Download fails — a partial zip is discarded automatically; just re-run run.cmd and it retries cleanly.

Where logs live

  • .bench/bench_run.log — benchmark run output from the plugin speed suite.
  • .bench/results-before.json / .bench/results-after.json — before/after hook-overhead measurements; .bench/rootcause-recovered.md has the 100x narrative.
  • ollama/runtime/ (repo root, or ~/.xomni/ollama/runtime) — the bundled portable Ollama runtime; OLLAMA_MODELS (default ~/.ollama/models) holds pulled models.
  • Your config, keys, and memory live outside the repo checkout — updates never clobber them.

Still stuck?

  • Verify the install: cd plugins/repomap && python -m unittest tests.test_core -v (15 tests); full suite is 647/647.
  • Re-read Install, FAQ, and BYO Provider — most issues are covered there.
  • Open an issue at github.com/painbaba/xomni with the relevant log from above.
