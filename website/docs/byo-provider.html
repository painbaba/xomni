Bring Your Own Provider

XOMNI ships with 25 verified free models, but the provider-pool plugin is built for your keys too. Add any OpenAI-compatible endpoint — hosted or local — and the pool routes around it automatically.

Why bring your own?

  • Higher ceilings. Paid models can beat free ones on hard tasks; the pool prefers free unless you say otherwise.
  • Privacy. Route sensitive work to your own endpoint or a local model.
  • Reliability. If a free model drops out mid-task, the pool fails over to the next provider.
  • Compatibility. Any OpenAI-compatible API works — no vendor SDKs.

Add a provider

Keys live in the XOMNI config file (outside the repo checkout). Add a provider block:

xomni.config.json
{
  "providers": [
    { "id": "my-openai", "baseUrl": "https://api.openai.com/v1",
      "apiKey": "env:OPENAI_API_KEY", "priority": 5 },
    { "id": "my-local", "baseUrl": "http://localhost:11434/v1",
      "priority": 9 }
  ]
}

apiKey accepts an env:VAR reference so secrets never sit in plaintext files. Lower priority numbers are tried first. Local endpoints don't need a key at all.

Local models

The local-models plugin lets you mix GGUF models running on your own machine into the same pool. XOMNI treats them as just another provider:

  • Serve a GGUF via any OpenAI-compatible local server (e.g. llama.cpp or Ollama).
  • Add it as a provider with "local": true.
  • Use the local-only routing flag for tasks that must never leave the machine.

Verify the pool

bash
$ xomni models --list
$ xomni models --verify   # re-checks every provider, free and BYO

Failed providers are marked down and skipped until they pass again. The pool re-verifies automatically on a schedule.

Keeping secrets safe

Never commit keys. Use env: references, or the interactive xomni config set provider.<id>.apiKey command, which stores the key in your OS keychain where available. See Security for the full threat model.
