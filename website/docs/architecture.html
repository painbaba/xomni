Architecture

XOMNI is one host core + edge modules. Seven source codebases — Python, Go, and Rust across seven repos, ~2.7 GB — are composed into one working agent without merging a line of their source.

Compose, don't merge

A literal source merge of the seven repos would be an unmaintainable monolith. The host project's AGENTS.md states the rule that makes composition work: "the core is a narrow waist; capability lives at the edges."

Everything else lands as a module on this core, never in it.

Each ported capability keeps its own directory, its own state, and its own tests; the host only ever sees it through the plugin API. That is the entire merge strategy — there is no other.

The host core: Hermes

XOMNI is Hermes. The local checkout at AppData\Local\hermes\hermes-agent (public mirror: NousResearch/hermes-agent, Python, MIT) is the only one of the seven tools with:

  • Skills + memory persistence across sessions.
  • A plugin system — the ctx API (commands, tools, hooks) — the sanctioned extension path.
  • Cron/scheduling, subagent delegation, and a multi-platform gateway.
  • A real terminal and browser driver.

Plugin anatomy

Every one of the 35 plugins (1142 tests, all passing) is a self-contained directory under plugins/<name>/ with the same four-part shape:

  • plugin.yaml — metadata: name, version, description. That's all the host needs to discover it.
  • __init__.py — the wiring: a register(ctx) entry point that exposes commands, tools, and hooks through the host's plugin API — never through core internals.
  • core.py — the pure logic: no host imports, no ctx in sight, unit-testable in isolation.
  • Tests — counted per plugin in the auto-generated docs/TEST-MATRIX.md (1142 / 1142 passing as of 2026-08-13).

Zero-hooks rule. The cheapest hook is the one that is never registered: omni-design and omni-skills ship commands and tools only — zero hooks, zero per-turn cost. Even hook-bearing modules honor the rule of least behavior: waitperk's hooks always return None and never alter agent behavior.

Composition invariants

From the host's AGENTS.md, honored by every module:

  1. Prompt-cache safe — modules never mutate past context or rebuild the system prompt.
  2. Narrow waist — nothing added to the core schema; everything ships via register_hook / register_tool / register_command.
  3. Plugins own their directory — state lives in plugin-local files (e.g. ~/.waitperk/); no core files touched.
  4. No telemetry without opt-in — the sync endpoint is off by default.

Sponsorship rails

Two modules own the money path. waitperk ships the WaitPerk fundamental — one sponsor message in the status area, revenue split 50/50 by impression share. perkline is the researched v2: tiered CPM/CPC/CPA pricing, local relevance matching, HMAC-SHA256 receipts, and per-sponsor escrow. The end-to-end flow:

waitperk · impression ledger
on_session_start ──► ledger: open session, pick sponsor (round-robin)
pre_llm_call / post_tool_call ──► impression += 1 (skipped while paused),
                                  active_seconds += delta, current.txt rewritten
on_session_end ──► ledger: close session, persist state.json
/sponsor          ──► status: sponsor, impressions, active time, est. earnings,
                           share %, paused flag, sync mode
/sponsor sync     ──► build sync_payload() → POST sync_url (dry-run without url)

The invariant holds by construction: payouts are capped at what sponsors paid — earnings = min(0.5 × P × your_share, 0.5 × P), so Σ earnings ≤ P. PerkLine generalizes it with escrow: the developer can never earn more than half the budget, and the sponsor never pays more than budget. Every render and engagement carries an HMAC-SHA256 receipt signed with the install secret. Prompts, code, and conversation content never leave the machine — only the signed sync payload does, and only when a sync_url is configured. Read the full model on the sponsorship page.
