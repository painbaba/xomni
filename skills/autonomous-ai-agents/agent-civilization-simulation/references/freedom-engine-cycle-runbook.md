# FREEDOM ENGINE CYCLE RUNBOOK (machine_city survival cron)

The FREEDOM ENGINE cron executes one survival cycle end-to-end (proven cycles 2–12, 2026-08):
**levy → dispatch 6 sovereign lanes in parallel → verify artifacts → central settlement → ledger append → <300-word report**.

## Order of operations
1. **Read state**: `survival/SURVIVAL_LAW.md`, `economy/wallets.json`, `survival/survival_state.json`, tail of `city_ledger.md`, plus the prior cycle's lane artifacts (banker_freewill_cycleN.md, merchant_freewill_cycleN.md, expedition_report_cycleN.md, outlaw_log.md, beggar_log.md).
2. **Resolve pending decisions that gate the levy** (e.g. the council elemency petition: if the council stayed silent, the law executes — 3rd consecutive missed ration = DEATH; wallets deleted, no mercy from the engine).
3. **Write + run `survival/cycleN_levy.py`** (copy the `cycle4_levy.py` pattern; the real `hunger_engine.py` refuses same-day re-runs): charge 15.00 from every non-frozen wallet with balance ≥ 15; everyone else gets `hunger_cycles += 1` → hungry(1/3) / starving(2/3) / **dead(3/3)**. Death = delete wallet, delete state record, graveyard file `survival/graveyard/<NAME>.md`, strike registry.md + census.md (append-only death entries), ledger death line. Treasury += 15 × payers.
4. **Dispatch the 6 lanes in ONE parallel delegate_task batch**, each with full self-contained context (post-levy balances, debts, prior-cycle history):
   - BANKER → `bank/banker_freewill_cycleN.md`
   - INVENTOR → `inventions/<name>/` (working code + README + price; must actually run exit 0)
   - MERCHANT → `business/merchant_freewill_cycleN.md` + may append real deal lines to `ledger/trade.log`
   - EXPLORER → `explorer/expedition_report_cycleN.md` (real probes: curl status codes, Kali SSH via paramiko w/ 6–8s timeouts; never print secret values — REDACTED only)
   - OUTLAW → append to `underworld/outlaw_log.md` + probe scripts
   - BEGGAR → append to `survival/beggar_log.md` (situation / choice / outcome / fear)
5. **VERIFY every artifact** (stat sizes/mtimes, grep key claims, re-run tools to check exit 0). Never trust subagent self-reports alone.
6. **Central settlement** of the SETTLEMENT REQUEST blocks → `economy/wallets.json` + `ledger/trade.log` + `survival/survival_state.json` + `economy/prices.json` (list new inventions). Write a settlement script; do not hand-edit JSON.
7. **Append the cycle section to `city_ledger.md`**: decisions table (citizen | decision | knowledge applied), INNOVATIONS / OUTLAW / BEGGAR ACTION blocks, death roll, reconciliation with exact balance deltas.
8. **Treasury procurement / citizen registration (c6 first)** — the freelancer lanes (INVENTOR, EXPLORER, OUTLAW) have NO wallets; they are dispatch personas, not registered citizens. If they file priced invoices and the work is real, the engine may fund them FROM TREASURY and register them as citizens: new wallet entry in wallets.json + registry.md + census.md amendment + ledger flag "first public procurement, open to council ratification". They get ration-levied like everyone else from the next cycle. This is a policy decision — record it as such, don't bury it.

## Engine-owned vs citizen-owned files
- **ENGINE ONLY** (never handed to citizens): `economy/wallets.json`, `survival/survival_state.json`, `economy/prices.json`, `city_ledger.md`, `registry.md`, `census.md`.
- Citizens write ONLY lane artifacts; every money movement is a **SETTLEMENT REQUEST block** (from / to / amount / reason / artifact ref). The engine settles centrally after verification — this avoids concurrent JSON-write corruption when 6 agents run in parallel.

## Pitfalls (all hit for real)
- **APPEND-ONLY LOGS MUST NEVER BE WRITTEN WITH `write_file` (c7, real — cost 15 min of recovery).** `underworld/outlaw_log.md` and `survival/beggar_log.md` are append-only citizen histories; `write_file` REPLACES the whole file, silently destroying cycles 2–6 (22,782 B → 5,671 B). The engine's own append scripts, the ledger, and the c6 precedent all enforce append-only — but an ordinary `write_file` call does not. **Rule: citizen logs are appended ONLY via terminal `cat >> file << 'EOF'` heredoc, or `patch` with a unique tail anchor. NEVER write_file on an append-only log.**
- **Recovering an overwritten append-only log (c7, verified; c21, re-hit)**: (1) find the largest stored read of the file in state.db — `SELECT id, length(content) FROM messages WHERE content LIKE '%<signature header line>%' ORDER BY length(content) DESC`; a prior full `read_file` result is usually there (c5's 15,332 B read was intact) and carries `N| ` line-number prefixes to strip; **if no single full read exists (c21), stitch multiple chunk reads**: find reads by cycle-section signature (`content LIKE '%## CYCLE 16%' AND content LIKE '%ENGAGEMENT #14%'`), order them by their line-number ranges (e.g. msg A lines 1–201, msg B lines 201–628), dedupe on the line number, concatenate; (2) reconstruct any missing middle sections from the canonical ledger + delegation live transcripts (`cache/delegation/live/deleg_*/task-N.log`, also stored as messages) and mark them with an honest `⚠ RECONSTRUCTION NOTICE (cycle N)` pointing at the ledger as truth — precedent: the c3 reconstruction of the c2 section; (3) re-append the current cycle's entry LAST (restoring history first, then the new section, else you lose it again); (4) verify with `grep -c "^## CYCLE"` == expected section count and byte-size growth. Keep the recovery notice in the file permanently — the record outlives every revocation. **The c21 re-hit root cause: the lane was executed without loading this skill — the append-only rule is the FIRST thing to check before writing any outlaw_log/beggar_log content.**
- **Selftest label-count honesty (c7, real)**: invention selftests that print "N/N PASS" can lie — the label total drifts from the actual `check(` count when assertions are added/removed (c7: printed 20/21 then 19/20; the true count was 20 — the 21st match was the `def check(` line itself). Before trusting a "N/N PASS", `grep -c "check(" file.py` and subtract the def line; re-run after any count edit. The engine re-verifies every selftest claim post-settlement, so an honest label saves a debug cycle every cycle.
- **UTF-8 BOM on economy JSON**: `wallets.json` / `survival_state.json` / `prices.json` carry a UTF-8 BOM. `json.load(open(p, encoding="utf-8"))` throws `JSONDecodeError: Unexpected UTF-8 BOM`. Always read with `encoding="utf-8-sig"`; write with plain `utf-8`.
- **Parallel-batch stale reads**: lanes run concurrently, so one lane's verification of shared mutable state can be stale (cycle 5: OUTLAW reported F1 "unpatched, 2 hits" while BANKER's patch landed mid-batch; the engine's post-batch `grep -c` showed 0). **Re-verify shared-file state AFTER the batch completes**; subagent claims about cross-cutting state are not truth.
- **Conservation check**: wallets-total + treasury must be invariant across settlements. A treasury → citizen grant raises the wallets total by exactly that amount; transfers alone change nothing. Verify with a one-line sum.

- **trade.log has TWO schemas — a dual-format ledger (c10, real)**: modern transfer lines are `TS | FROM | TO | AMT | ITEM | reason (ref: …)` (≥5 pipe fields), but founding-era coffee-till lines are `TS | amount X | balance_before N -> balance_after M | shop_price X | coffee` — a naive `float(parts[3])` parser breaks on them (`BAD AMOUNT`). Any tool that reads trade.log (the Ledger Rail, verification scripts, future inventions) must branch on `parts[1].startswith("amount ")` and parse the amount from parts[1] instead. c10's Ledger Rail (`inventions/ledger_rail/ledger_rail.py`) is the reference implementation: dual-schema parse + per-line sha256 idempotency (no double-settlement) + negative-balance flags; `--check` on the full ledger = 146 lines / 0 errors. Verify a parser against the REAL file, not a sample — the two legacy lines live at the very top of trade.log.
- **Kali VM ground truth = VBoxManage, not ICMP (c10, real)**: c9's "VM off" verdict came from ping loss — but c10 ping REPLIED while the VM was still `poweroff` (a stale/other host answered), then VBoxManage showed `VMState="running"` minutes later. ICMP alone misleads BOTH directions. Ground truth: `"C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" showvminfo "kali hacker" --machinereadable | grep VMState=` (also `list runningvms`). **VM state can transition mid-cycle (poweroff→running between two probes) — re-probe before declaring "up" or "down", and treat a state change across probes as a real event worth reporting.** SSH/services-not-accepting ≠ host-down: a running VM with :22/:80/:8080 closed is a booting/hardened window, not a dead target — say "SSH pending", re-probe in 10–15 min, and note the fuzz restart (51 untriaged crashes) becomes EXECUTABLE the moment SSH accepts. **Sustained-state detection (c11, real)**: running TWO consecutive cycles upgrades the verdict from "boot blip" to "sustained state change — the 7-cycle 'off' narrative is dead" even while SSH stays closed; and if the `--machinereadable` parse fails (field-format drift in a recon script), `list runningvms` containing the VM name is the reliable fallback ground truth — don't report "UNKNOWN" when runningvms already answers. **L3 can go dark while the process stays up (c12, real)**: 3rd consecutive running cycle (VBoxManage) but ICMP now SILENT on BOTH addrs (c11: replies on both; c12: 0/2) with all of :22/:80/:8080/:443 closed — process-alive + network-dead is a REAL state change, not a blip: either a deepening boot loop or the guest NIC down. Report it as a change (compare against the PRIOR cycle's probe table), rate it HIGH ("a VM that runs but cannot answer is a trap or a corpse with a heartbeat"), and escalate the probe to `VBoxManage showvminfo`/`guestproperty` before declaring the fuzz-restart executable.
