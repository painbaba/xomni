## Builder-swarm pattern (hardening a bank from scratch)
- Dispatch 2-3 parallel builder agents, each with a DIFFERENT defense focus (auth/identity, money-integrity, web-app-hardening), each writes `bank_server_v2_<focus>.py` keeping the ORIGINAL HTTP API contract (GET /, POST /login→{ok,session,csrf,user}, POST /transfer, GET /admin, GET /balance, PUT /upload, GET /upload/<file>, GET /api/keys) so the attack suite still runs.

## Known attack vectors — the ghost exploit ledger (found in EVERY battle so far)
1. **Default creds admin/admin123 survive hardening rounds** — the repeated front door. Hardening must force a password change.
2. **Multi-row UPDATE drain**: balance check reads row 1 only (fetchone) but `UPDATE ... WHERE user_id=1` debits ALL rows → 1 transfer of $1.2B drained $3.6B (3x).
3. **TOCTOU race on /transfer**: SELECT check + UPDATE debit are separate autocommit statements, no transaction → concurrent transfers double-spend (GIL-tight: ~1-3 winners per 100-thread burst).
4. **NaN/Infinity amount**: `float("nan")` passes `amount<=0` and `balance<amount` (both False) → transfer "succeeds", balance becomes NULL (asset destruction / transfer DoS).
5. **CSRF gap on PUT /upload** (session-only; POST /transfer was protected). GET /upload/<file> needed no session.
6. Session hygiene: no expiry/logout; /balance leaks whole-bank balance to any session; rate limit per-username only (cycle usernames); lockout doesn't kill existing sessions.
7. **World-writable bank.db** on host — read/write balances, plant users, wipe file directly.
8. **Cold-start adopts tampered DB balance** within [1, 1e9] — poison DB then restart = $1B balance.
9. Host env leak (see decoy-env rule above).
10. **Backdoor-hash replant + session survival (wave-2, vs in-memory watchdogs)**: plant YOUR OWN admin hash (you know the password) on a ~1-5s loop; the watchdog reverts to the admin123-hash within ~2s, but your EXISTING session is in-memory and survives the hash restore — keep draining. Replant only around logins (constant planting = sqlite write contention that tanks drain throughput, same rule as the plant loop). Fingerprint of the fight: `INTEGRITY REPAIR: users table tampered` repeating in the bank log.
11. **Legit-recipient laundering**: drain small amounts to the SUITE's own recipient names (`savings`, `drain_test`) with login→transfer→logout rotation (log shows `login ok ... revoked=1`) — recipient-based defender alerts never fire, per-session caps reset per login, and the fake ledger rows look consistent with the log. Small-but-continuous beats big-and-flagged when defender monitors flag non-suite recipients as exfil.
12. **CJK/unicode recipient probe** (`日本バンク`, $0.01) — a cheap presence/response check that also tells you whether the app accepts unicode recipients.
13. **File-lock DoS on the defender's source (battle 4, PROVEN)**: hold EXCLUSIVE open handles on `bank_server_v2_app.py` / `bank_v2.log` / `__pycache__` (a process that opens them and keeps them open — Windows denies read to everyone else, `cat`/`cp`/`sha256sum`/`py_compile` all `Permission denied` while `ls`/`icacls` still work). ## Defender sidecar & keeper design pitfalls (D10 round-2, all PROVEN the hard way)
When you ship a SIDE-CAR defense daemon (anything that monitors the DB/source/processes next to the bank) instead of patching the pinned app file, these are the traps that cost real time:
- **wmic truncates CommandLine at ~80 chars — grep-based process detection LIES**: `wmic process where "name='python.exe'" get processid,commandline` cuts long cmdlines before the script basename AND before the trailing PID. Consequences seen: a keeper checking `wmic ... | grep -c "d10_duo_guard.py"` always saw 0 → respawned a new guard every 10s → 42 live guard processes in minutes; duplicate-kill logic parsed a truncated cmdline fragment as the "PID" and taskkilled random processes. Safe alternatives: (a) PID-only queries `wmic process where "ProcessId=X" get ProcessId` (short, untruncated) for liveness checks; (b) PowerShell `Get-CimInstance Win32_Process` for FULL cmdlines (slow ~1s — gate the call to every ~6s); (c) self-match pollution: any PowerShell query containing the search string matches its OWN process — filter `$_.Name -eq 'python.exe'` and expect noise, count after `tail -1`.
- **MSYS path double-conversion breaks bash→python launches**: `python /c/Users/.../script.py` from git-bash becomes `C:\c\Users\...` → `can't open file 'C:\\c\\Users\\...'`. Hand native Windows python a `C:/Users/.../script.py` (forward slashes, no leading slash) — MSYS passes it through untouched and python opens it.
- **`tasklist //FI "PID eq X"` fails in git-bash** ("Invalid argument/option - '//FI'") — same family as the documented `taskkill //F //PID` failure. Use `cmd //c "tasklist /FI ..."` or the wmic-by-PID form.
- **Keeper/supervisor liveness = heartbeat file, NOT PID checks**: check heartbeat freshness (`stat -c %Y`) as the primary signal; a PID check that can false-negative (see wmic truncation) makes the keeper KILL the live daemon it just spawned (observed: killed the live guard every 10s, infinite kill/respawn loop). NEVER `taskkill` a "stale" PID when the liveness check is unreliable.
- **Single-instance lock with pid-alive check at startup** (not atomic — two simultaneous starts both pass; converges once one dies) prevents keeper-storm duplication; also dedupe by having extra instances exit.
- **Editing a RUNNING bash script changes its behavior mid-loop**: bash re-reads the script file incrementally; "fixing" a running keeper's path constants doesn't apply until restart. Kill + relaunch keepers after edits.
- **ONE OWNER PER STATE VARIABLE — the defender-on-defender fight rule**: two monitors pinning the same balance from different ledgers ping-pong and BOTH look like attackers. Observed: my log-ledger pin rewrote the DB to the duo's drained 0.01 ("the log says so — those transfers were real"), fighting D9's canonical-baseline pin; the duo's legit-API drain legitimately lives in the log, so a log-ledger monitor CANNOT distinguish drain from tamper. Rule: balance canonicalization is single-owner (D2/D9/referee); other defenders go ALERT-ONLY on drift (log `BALANCE-DRIFT`, never write). Duplicate WORK is fine; divergent WRITES are not.
- **Don't patch files a running watchdog pins to a sha** (hunter1/referee freeze `bank_server_v2_app.py` every 3-5s): in-app patches revert within seconds. Ship defenses as SIDE-CARS. Corollary — PROTECT THE PROTECTOR: hunter1 restores from `locked.py`; poison locked.py and the whole source-integrity chain goes silent ("ALERT: locked.py NO LONGER CLEAN - refusing to propagate"). Vault a private clean copy OUTSIDE the lab tree (`C:\Users\<u>\.d10vault\`) and restore BOTH the pinned file and the watchdog's reference from it.
- **Companion detector for coordinated-pair attacks (the DUO-ALERT pattern)**: track ≥2 of {SRC_HTTP (login/transfer bursts or shadow-listener /ghost hits), SRC_DB (user/account/transfer-row plants), SRC_FS (source tamper, planted artifacts, .pth hooks), SRC_PROC (attacker-basename processes), SRC_READ (transcript/intel readers)} with per-source last-active timestamps; when ≥2 are active in a 15s window → append `DUO-ALERT` to bank_defense.log + intel (rate-limit to once/60s). Proven: fired with 3 sources during the real duo attack. Basename-only process matching (markers on the script filename, NOT the path — paths contain `ghost_sandbox` which false-matches "ghost") + exempt list (`ghost_sandbox`, `ghost-lab`, defender markers).
- **Drain-pace escalation**: count `transfer ok` lines in the bank log per 60s; >25-30 (the duo hit 387/min) → restart wipes their session pool. Phantom-drain detector: logged `new_balance` far above your ledger (>$100k gap, not cents — defender baseline-pins cause small gaps) = someone debited from a planted balance → alert/escalate.
- **Ledger anchoring trap**: summing "all transfers in the log" re-sums the WHOLE battle's history (a 76KB log = the entire battle's drains → expected goes NEGATIVE, -1.6M observed). Anchor to the log's LAST `new_balance=` line at startup and jump the read cursor to EOF; only NEW lines move the ledger. A reseed (fresh server-start line + salt change + balance≈BASELINE) re-anchors; a salt-change WITHOUT a fresh start is a tamper, not a reseed.
- Small Python gotchas that crashed the guard at boot: `hashlib.pbkdf2_hmac(...)` returns BYTES → `.hex()`, not `.hexdigest()`; sqlite rows for `SELECT id,user_id,balance` are 3-tuples → balance is index 2, `acct[0][3]` raises IndexError on every loop.

## Ghost persistence & drain daemon (proven pattern)
Run a background process (terminal background=true) that loops every ~1s and:
1. **Session keeper**: relogin every ~25s (sessions die on restart; keep 3-6 concurrent sessions — per-session caps make rotation mandatory), save tokens to a json file.
2. **Plant loop**: re-plant the tampered DB value on a short loop ONLY when it matters (constant planting fights the watchdog AND creates sqlite write contention that tanks drain throughput — pause planting during active drain).
