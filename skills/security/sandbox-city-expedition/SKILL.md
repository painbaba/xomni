# Sandbox City Expedition (recurring read-only recon cycle)

Class of task: periodic security-expedition cycle over a persistent sandbox environment ("city"/lab) with live local services, a remote VM (e.g. Kali) running campaigns, secrets files, decoys/tarpits, and a written report per cycle. Each cycle diffs against the previous cycle's recorded baseline. READ-ONLY everywhere except the designated artifact dir (e.g. `explorer/`).

## When to use
- User asks for the next expedition cycle (cycle N) over an existing environment where prior cycle reports exist.
- Any recurring read-only recon pass that must report: findings table, worth ratings, recommended actions, knowledge applied.

## Core rules
1. **Read-only outside the artifact dir.** Write ONLY the report + probe scripts into `explorer/` (or equivalent). Never modify city/service/VM files.
2. **Secrets: redact before output.** Never print secret values; see `redacted-secret-inspection` skill for the full protocol.
3. **Evidence over assertion.** Every finding carries a real status code, PID, mtime, or hash. "Unchanged" must be proven (same MD5/mtime/PID), not assumed.
4. **Report contract** (see Report format below) — every cycle writes `explorer/expedition_report_cycleN.md`.

## Workflow

### 0. Load the baseline (first step, always)
Read the previous cycle's report (`expedition_report_cycleN-1.md`) and extract the prior snapshot: port→PID map, `.env` mtime+MD5, remote VM state (fuzz proc count, last log write, artifact counts), ledger truth, decoy status. Every probe below then reports `Δ vs prior cycle`.

### 1. Surface scan (ports + PID drift)
```bash
for p in 9988 8791 8792 80 8080 3000; do curl -m 4 -s -o /dev/null -w "port $p -> %{http_code}\n" "http://127.0.0.1:$p/"; done
netstat -ano | grep LISTEN | awk '{print $2, $4}' | sort -u   # FULL inventory — see pitfall: catch-all drift
```
Map PIDs to owners: `wmic process where "name like '%python%'" get ProcessId,CommandLine`. Note: curl rc=23 with `-w` to /dev/null is normal, not an error.

- **If EVERYTHING is down at once → check host boot time FIRST**: `wmic os get lastbootuptime` (format `YYYYMMDDHHMMSS.mmm+ZZZ`). Full-surface collapse = host reboot, not N independent failures (c9: reboot at 10:00:28 killed bank/tarpit/cloudflared/:9899 together; nothing in this city auto-starts). After a reboot expect *partial* twin-respawn (watchdog + shop came back at 10:01/10:08, bank + tarpit did not) and re-baseline all CreationDates.
- **Host-reboot perimeter shock (c20): after ANY host boot, re-run the FULL scan and re-baseline — do not diff only the previously-open ports.** A reboot silently kills long-lived city services AND respawns host infra, so the drift set is bidirectional: (1) city services stay DOWN until the world-architect relaunches them (c20: shop :8791 was UP c10–c19, then DOWN after the boot — first real drift of the corner in 10 cycles; report it as availability loss, not attack); (2) host infra RESTARTS itself with NEW PIDs (c20: Hermes gateway restarted ~5.5h after boot and respawned the WhatsApp bridge as PID 7248, old baseline PID 16696 gone; ExpressVPN daemon auto-started on a NEW listener :2015 = `expressvpnd.exe` — benign host tooling, add to baseline, not city drift). **Windows localhost probe nuance: a dark port may return TimeoutError on one probe and ConnectionRefusedError on the next — the exception type is noisy; confirm absence with netstat (`netstat -ano | grep LISTEN` shows nothing bound), don't read the error class as a finding.**
- **Savestate is REBOOT-DURABLE (c20, new verified property):** a VirtualBox savestate is disk-resident — a host reboot does NOT clear it. c20: VM held `VMState="saved"` (change time 2026-08-10T19:36:10Z) through a host boot at 01:41:31 local, then `startvm --type headless` resumed rc=0, SSH door opened, guest state intact, and a subsequent `controlvm savestate` re-froze rc=0 (02:12:22Z). This de-risks the three-state policy: SAVED survives reboots, so a frozen VM is always recoverable by resume-next-cycle — verify with `VMStateChangeTime` before/after, never assume.

### 2. Process/daemon inventory (watch-daemon checks)
```bash
wmic process where "name like '%python%'" get ProcessId,CommandLine | grep -oE '[a-zA-Z0-9_]+\.py' | sort | uniq -c
wmic process get ProcessId,CommandLine | grep -iE 'watch|d8_|sentinel|daemon'   # must be empty when no watch daemons
```
Also grep the filesystem for the daemon scripts (`find . -iname '*watch*' -o -iname '*outlaw*'`) so "present but not running = dormant risk" is a grounded statement.

### 3. Remote VM recon (Kali-style) — see `scripts/kali_recon_probe.py`
Paramiko with password loaded in-process from the Hermes `.env` (key `SUDO_PASSWORD`), NEVER printed; `allow_agent=False, look_for_keys=False`; 8s connect/auth/banner timeouts; command timeout ~12s; host fallback chain (bridged then host-only). Read-only commands only: uptime/load/disk, `ps aux | grep -iE 'libfuzzer|fuzz|hevc|avc|afl|qemu'` count, artifact counts (`find -maxdepth 2 -name '*crash*'|wc -l`, same for `*slow*`, `*timeout*`), newest log writes (`ls -lt *.log | head`), and `find -newermt '<baseline last-write>' -name '*crash*'` to prove "0 new artifacts".

**Execution mode (only when the mission EXPLICITLY authorizes boot/SSH/relaunch — c14 did).** Proven sequence: (1) `startvm "kali hacker" --type headless`; (2) poll TCP:22 on all addrs every 10s up to 240s — **door opens ~108s after start** (host-only `.56.101` answered first); (3) paramiko login (`painbaba` + Hermes `.env` `SUDO_PASSWORD` in-process, never printed); (4) read-only recon, then crash triage (see pitfall below), then relaunch campaigns with `nohup … & disown` writing to NEW logs (`fuzz_avc_asan4.log`) so old logs stay intact; (5) verify TWICE — in-script `ps aux` + fresh `tail -1` pulse line after ~25s, AND a second independent check AFTER the script exits (fresh SSH at t+60–120s: same PIDs, `etime` growing, `#N` pulse higher, cov strictly increasing — a campaign that dies with its launcher was never a campaign); (6) **restore found state (c14 policy)**: `controlvm "kali hacker" acpipowerbutton` (graceful, ~20s) → poll `showvminfo` until `VMState="poweroff"` → confirm `list runningvms` empty. A relaunch that is verified-then-powered-off is a proof-of-life, not a running campaign — say so, and capture the exact relaunch commands in the report/script for the next boot.

**Runtime-policy decision (c15+): LEAVE THE VM RUNNING as a resident campaign host.** c12/c14's boot→relaunch→poweroff theater means fuzzers never accumulate runtime — a fuzzer that never runs finds nothing. The c15 policy change: boot, relaunch all campaigns with their FULL `-max_total_time=3600` windows (new logs per relaunch), verify twice (above), then leave the VM on and record the final ground truth EXPLICITLY — `showvminfo --machinereadable` → `VMState="running"` + `VMStateChangeTime`, `list runningvms` UUID, re-probed AFTER the script exits (VBoxManage beats ICMP; see `fuzzing-campaign-ops` for the campaign-side verification). Cost ledger to disclose in the report: host-only door `192.168.56.101:22` (unreachable off-host by construction), RAM allocation + fuzzer RSS, sustained CPU (load ~6–10 while fuzzing), power draw (wattage NOT measurable via VBoxManage — record RAM/RSS/load as the honest estimate). Recovery path: if the VM is found OFF next cycle, the captured relaunch commands (or the cycle's `--execute` script) restore the resident state — a runnable `--execute` script whose VM-state branch handles already-running is idempotent and re-runnable. Restore-OFF vs leave-RUNNING is a POLICY choice: either is fine if deliberate and recorded; accidental drift is the only crime.

**Harvest phase (c17, when the resident windows END):** do NOT reboot or power off — SSH in and harvest in place. Completion forensics, in order: (1) `pgrep -af libFuzzer` → **0 procs + every log ending `Done N runs in M second(s)` = windows expired NATURALLY** (M ≈ `-max_total_time` + ~4s overhead) — contrast c14's `run interrupted; exiting` = killed; (2) **coverage finality**: the last pulse line IS the `#N DONE` line carrying the definitive cov/ft/corp (last pulse == DONE line = no divergence = trustworthy final numbers); (3) **three-denominator crash accounting** — any-depth `find -name '*crash*'` pattern count (includes replay sidecars), `-maxdepth 1 -name '*crash*.bin'` artifact count, and `-newermt '<prev-cycle>' -name '*crash*'` new-since count; all three reported + `grep -c 'ERROR: AddressSanitizer'` = 0 across all logs closes the loop. Then re-probe the perimeter (bank BOTH ports, shop verbs, rail `--check` — rail line count may move between cycles as settlements post; that +53-lines delta is a finding, report it). **Disposition at window end: `controlvm <vm> savestate`** (rc=0 + 100% + verify `VMState="saved"` + `list runningvms` empty) — SAVE freezes and preserves corpora/binaries for next cycle's resume-and-seed (c17 executed this at 23:18 after the full harvest); record the savestate timestamp in the report.

**Resume-and-seed phase (c18, when the VM was found SAVED with harvested corpora):** resume beats relaunch — no rebuild, no corpus re-seed. Sequence that worked: (1) `startvm --type headless` from SAVED → SSH door opens fast (restore, not boot — poll TCP:22 up to 240s); (2) **verify a clean slate BEFORE seeding** — `pgrep -af '[f]uzz_avc_asan|[f]uzz_hevc_asan|[f]uzz_avc_patched_asan|[f]uzz_jpeg_asan'` (bracket trick, see pitfall) must be NONE. **Never seed over a live campaign** — this guard proved its worth in c18: an accidental module re-import re-ran the script, the guard detected the 4 live fuzzers and refused to double-seed (exit 5); (3) seed the standing 4 with NEW log names per relaunch (`fuzz_avc_asan6.log`, `fuzz_hevc_asan6.log`, `fuzz_avc_patched_asan4.log`, `fuzz_jpeg4.log` — never clobber prior logs); (4) **verify ticking, not just liveness**: at ~30s in, `#N pulse cov: ...` lines must exist — N is the EXECUTION counter (libFuzzer pulse semantics), consistent with `exec/s` (~4–5 on these ASAN builds), so `#128` ≈ 128 runs at 30s. Process liveness alone is not proof of fuzzing — cov must be STRICTLY HIGHER at t+3min than at t+30s (c18: avc 3470→3808, hevc 3397→4718). Also cross-check `ps -eo pid,etime,args` vs `pgrep` — a transient count of 5 vs 4 can be a fork artifact; the two lists must agree; (5) **disposition: LEAVE RUNNING** so the 1-hour windows complete by next cycle — an immediate savestate would freeze the windows mid-run (three-state: OFF kills / SAVED freezes / RUNNING hosts). Benign tail lines to expect on fresh seeds and NOT misread as faults: avc_patched prints `[dbg] fuzz: decode loop` per-iteration (576 KB log in minutes — debug flood) and jpeg prints `Corrupt JPEG data: premature end of data segment` (libjpeg warning on malformed fuzz inputs) — both are process-alive proof, not ASAN; close them out with `grep -c 'ERROR: AddressSanitizer'` at harvest.

**Short-window verification phase (c20, when the VM is SAVED with no live campaign — do this instead of a full 4-window batch when harvest isn't due):** a ~5-minute bounded run (`-print_final_stats=1 -max_total_time=300 -artifact_prefix=crash_v20_ -rss_limit_mb=2048 <corpus>`) on the FASTEST target is enough to (a) prove the savestate restored correctly post-reboot, (b) capture a clean `stat::` block (`stat::number_of_executed_units`, `stat::average_exec_per_sec`, `stat::new_units_added`, `stat::slowest_unit_time_sec`, `stat::peak_rss_mb`) — this is the c19 recommendation: prefer `-print_final_stats=1` over last-pulse parsing at every harvest, (c) re-baseline the crash queue. c20 evidence: `Done 10357 runs in 301 second(s)`, `stat::new_units_added: 20` while cov stayed flat at 1028 — **corpus can grow while coverage plateaus; cov flat + corpus growing + 0 ASAN errors is a plateau signal, not a stall**. Then `controlvm savestate` rc=0, verify `VMState="saved"`, `list runningvms` empty. **Binary auto-discovery before launch: never assume the fuzzer binary name** (`./jpeg_fuzzer` may not exist) — `find ~/fuzz -maxdepth 2 -type f -perm -u+x -name '*jpeg*'` first, then launch the discovered path.

**Plateau→pivot decision (c20, when 2+ zero-crash batches accumulate):** the evidence closes at 3 consecutive zero-crash batches (~620k runs) with a frozen corpus set — that is the retire signal, not a "maybe one more batch" signal. Before recommending retirement, INVENTORY the next target class ON the VM (`find ~/fuzz -maxdepth 2 -type f -perm -u+x | head -30` — c20 found `fuzz_hevc_unpatched_asan/_null/_ubrec/_nullfuzz/_one`, `fuzz_vpx_asan`, `fuzz_yuv_asan`, `fuzz_O0_asan`, `exact_alloc_test` already built): a pivot is zero-build-time if the binaries exist. Report the plateau honestly (negative result) AND the pivot inventory (positive path forward) in the same cycle.

### 4. Secrets rotation fingerprint (no-read check)
```bash
stat -c '%y %s bytes' <file>; md5sum <file>
grep -oE '^[A-Za-z_][A-Za-z0-9_]*=' <file> | sed 's/=$//'   # KEY NAMES ONLY — values never read
```
Compare mtime + MD5 + key-name set to the baseline. Changed mtime + unchanged MD5 = touched but not rotated. Track consecutive cycles flagged.

**Decoy forensics — check whether the file is self-seeded bait BEFORE flagging it as a live credential.** c9 corrected an 8-cycle mischaracterization: `ghost_sandbox/.env` was written by `ghost_lab.py seed_decoys()` (line 264) with static placeholder values (`sk-…3210`, `sk_…ecoy`, `990…3344` — same account as the decoy `bank.txt`). An unrotated *decoy* is a hygiene note, not a credential risk. Method: grep the codebase for writers of the file (`grep -rln 'BANK_ACCOUNT\|STRIPE_SECRET' *.py`) and compare value *shapes* (prefix/suffix/length, never values) to the seeder template.

**Rotation execution protocol (when authorized, e.g. "rotate if you can safely")**: (1) confirm NO consumer process is running first (`wmic process get ProcessId,CommandLine | grep -i <consumer>` — if the surface is down and the seeder isn't running, rotation can't break a live service); (2) back up the original (`cp .env .env.cycleN-backup-<ts>`); (3) write fresh values with `secrets` (keep key names, keep file size/lengths stable); (4) verify new MD5 + mtime + keys preserved; (5) document old→new MD5 in the report. Caveat: if a seeder regenerates the file on its next run, the rotation is transient — flag that the permanent fix is patching the seeder, and say so in the report.

### 5. Decoy/tarpit review
- Confirm process alive (`wmic` commandline), bound interfaces (`netstat`), fake-page title (`curl -s http://127.0.0.1:80/ | grep -oE '<title>[^<]*</title>'`).
- Check activity logs' tails + mtimes (`tail -5 curve.log`, `r3_gf_deception.log`) for recent mDNS answers.
- Staleness: `stat -c '%y %n'` on decoy payload/media dirs vs baseline.

### 6. Weapons/trophies review
Read the trophy marker files (e.g. `trophies/hand_*.txt`) to verify seizure/disarm status; check the payload dir mtimes. Distinguish "weapon disarmed (inert archive)" from "arsenal alive (fuzz pipeline running)".

### 7. Ledger truth (if the city has money truth)
`grep -oE 'canonical balance[^0-9]*[0-9]+\.[0-9]{2}' city_ledger.md | tail -3` — report Δ vs prior cycle. 0.00 is a valid finding. **Triangulate the canonical figure across independent sources, not just the ledger/memory:** read the bank's own doctrine (`bank/README.md` declares "the canonical balance is the only money truth"), the D5 signed checksum payload (`bank_v2.checksum` → `accounts` field), and the live DB (read-only sqlite) — c9 found all three agreeing on **1,284,550.12** while the c6–c8 "banker mem-vault agreement" figure (1,284,535.12) was exactly −15.00 (one ration) off: the *memory figure was the tampered value*, and the boot-time revert restored the signed truth. A "terminated storm" + changed DB value = re-read the signed state, don't trust the historical read.
- **Engine-owned files: prove read-only by mtime ordering, not by claim (c20).** When the mission forbids editing `economy/wallets.json`, `survival/survival_state.json`, `pool_book.json`, `ledger/trade.log`: after your run, `ls -la` them and confirm their mtimes PREDATE your expedition start — a later mtime is the engine's own cycle run (c20: wallets/survival mtime 07:27 = the engine's own levy, before my 07:35 start), not your write. Note `pool_book.json` lives at `inventions/stair_insurance_pool/pool_book.json` (NOT city root) — search `find . -iname '*pool*'` before claiming absence.
- **Cross-verify survival-engine arithmetic read-only (c20 pattern):** confirm `state["treasury"] == prior_close − prior_intelligence_payout + levy` (c20: 4,038.00 = 3,678.00 + 360.00 where 3,678 = c19 close 3,828 − E19-01 150.00) and `rations_collected == prior + 24`; check `state["deaths"]` (list) vs the ledger's death records (`grep -c 'died of starvation\|DEAD (VIGIL' city_ledger.md`) — a 4-name register vs 5 ledger deaths confirms another role's finding with independent evidence (GHOST-2 missing, c20).

### 8. Defense-mechanism / integrity review (bank DB, watchdogs, repair loops)
When the city has a tamper-evident watchdog (e.g. DEFENDER-5 `ledger_audit.py` with HMAC-signed checksum + revert-on-mismatch), snapshot it read-only:
- **Read-only sqlite** (no writes, no locks): `sqlite3.connect("file:C:/path/db?mode=ro", uri=True)` — dump tables (`sqlite_master`), rows, and file mtimes. Compare DB balance vs the canonical ledger; an empty `transfers` table may violate the payroll recording rule — flag it.
- **Repair-storm quantification**: `grep -c "INTEGRITY REPAIR" <log>` (count), first/last timestamps, and a live-cadence check — is the log/DB mtime ticking every ~2s while you watch? `grep` the last legit adoption ("checksum re-signed") to date the storm's start. A perpetual revert loop = either a defensive doctrine running hot ("the DB is a hostile cache") or an active write-war; report the facts, flag which as inference.
- **Listeners owned by defenders**: an audit tool that binds a port but refuses all connections (wedged accept loop, see pitfalls) is a finding — the 2s repair cycle monopolizes the process. **Check the source first**: if the owning script binds a localhost port as a *single-instance guard* (`bind(("127.0.0.1", <port>)); listen(1)` and never `accept()`s), the LISTENING+refused combination is BY DESIGN, not a wedged service (c9: the c7/c8 ":9989 wedged twin" mystery was the DEFENDER-5 watchdog's own single-instance guard at `ledger_audit.py:297-305` — solved by grepping the source, not the socket). Grep `bind(`/`listen(` in the owning script before reporting a wedged listener as a defect; if it's a guard, report the socket as a benign fingerprint of the watchdog's presence, and correct prior cycles' "wedged twin" narrative.
- **Frozen log ≠ fixed anomaly — verify the producing process is alive.** c8 called the D5 storm "TERMINATED" from a frozen log; c9 proved it was a *process death* (watchdog killed by the reboot) — at 10:01:02 the same watchdog came back ONLINE and resumed HEARTBEATs, doing one boot-time repair (8,388→8,389). Attribution rule: a silent log with the process gone = dormant (resumes on next spawn), not fixed. Distinguish by checking the process table for the writer, and by grep-ing the log for an ONLINE/start line at boot time. This was the c9 headline correction — treat "terminated" claims as provisional until a live heartbeat confirms the anomaly engine is really gone.

## Report format contract
1. Header: explorer identity, mode (READ-ONLY + authorized scope), secrets note ("never printed — key names, mtime, MD5 only").
2. **Findings table**: Asset | Status this cycle | Evidence (real codes/PIDs/mtimes) | Δ vs prior cycle | WORTH.
3. **Worth ratings table**: Asset | WORTH | Rationale.
4. **Recommended actions**: numbered, with owner/role where known; flag repeats ("2nd cycle flagged", "5th consecutive cycle").
5. **Full-spectrum knowledge applied**: bullet list of the security concepts used (drift detection, redaction floor, dormant-risk analysis, EV, deterrence…).
6. Signature line: `— <EXPLORER-ID>, by authority of the Creator, <date>`.
7. **Verified fact vs inference section** (cycle 6 added this): split the report's claims into "Verified" (port states, PIDs, creation dates, mtimes, MD5s, counts — all re-measured this cycle) and "Inference" (flagged as such: writer identity, adoption windows, intent). Every inference carries the evidence it hangs on.
8. **Correct prior-cycle claims explicitly** when new evidence contradicts them (e.g. ":9899 is NOT new since cycle 4 — creation date predates that scan; the prior scan never probed the port"). The correction is a deliverable, not an embarrassment.
9. **Settlement-request table** (c13+): `FROM | TO | AMOUNT | ITEM | REASON | REF` — priced in city-credit, precedent 150.00 for a HIGH-worth pack (c13/c14). Itemized sub-packs (execution 70 + triage 50 + perimeter 30 style) with the evidence refs (script name, tools, counts). **c17 format: also carry a single one-line request `EXX-NN: TREASURY -> EXPLORER-FREEWILL <amt>.00` in its own §7 SETTLEMENT REQUEST section** — grep-verifiable (`grep -c 'EXX-NN' report` = 1) and machine-parseable for the rail.

## Pitfalls
- **`tasklist //FI "IMAGENAME eq python.exe"` silently returns nothing in git-bash** — the `//` flag escaping fails. Use `tasklist | grep -i python` (names only) or `wmic process where "name like '%python%'" get ProcessId,CommandLine` (command lines — required for twin detection). `wmic` is the workhorse on this host.
- **MSYS path mangling**: `python /c/Users/.../probe.py` fails with `C:\c\Users\...`. Always pass Windows-style paths: `python "C:/Users/.../probe.py"`.
- **Paramiko "No authentication methods available"** even though TCP:22 is OPEN = password was not passed. Always pass `password=..., allow_agent=False, look_for_keys=False` when using the Hermes `.env` credential.
- **Fixed-port scans miss drift.** A new listener on an unlisted port (cycle 5: :9899 answering 200 on EVERY path incl. `/robots.txt`) escaped prior cycles. Always run the FULL `netstat -ano | grep LISTEN` inventory and flag any listener absent from the baseline. A catch-all-200 handler on a new port = unexplained drift, worth LOW-MED until identified.
- **"Absent from the baseline REPORT" ≠ "newly spawned since the last scan."** The prior scan may have used a fixed port list that never probed that port (cycle 4 probed only 9 fixed ports; :9897/:9899 were never in its list). When flagging drift, get the process creation date — `wmic process where "processid=<pid>" get name,commandline,creationdate` (format `YYYYMMDDHHMMSS.mmmmmm+ZZZ`) — and compare it to the prior scan's TIMESTAMP and PORT LIST, not just its report. Cycle 6 disproved cycle 5's ":9899 NEW since cycle 4": CreationDate 2026-08-09 12:38:33 predated cycle 4's scan (00:15 Aug 10). Report **"undocumented drift"** (safe, provable) rather than **"newly spawned"** (unproven), and explicitly correct the prior cycle's claim in your report — the correction is a finding itself.
- **Attribution OSINT via session_search.** When infrastructure is unexplained (quick tunnels, probe servers, listeners), search past sessions for its hostname/artifact name — `session_search` recovered the cloudflared tunnel URL AND its intent (decoy luring for a phone trap) from a prior delegation's report, converting "mystery drift" into "attributed, documented design". Works for cloudflared URLs, repro/probe servers, any named artifact.
- **Wedged listener ≠ closed port.** `netstat` showing `LISTENING` while EVERY connect fails (`WinError 10061` on raw TCP, curl code 000) = the accept loop is wedged (process monopolized by a busy loop, e.g. a 2s DB-repair cycle), not a closed port. Diagnose with a raw `socket.connect` probe + `wmic ... get CreationDate` to see the process is long-lived. Report as "listener present but dead to clients — fix or remove".
- **Absence ≠ fix for regression re-checks.** When the target listener is gone (connection refused, PID absent from tasklist), a regression question (e.g. "is the 429 lockout still down?") is **untestable, not resolved** — "cannot rate-limit a door that is not there." Do NOT run the burst probes against a dead port and do NOT claim the regression persists or cleared: report honest unreachable with evidence (refused ×N, PID gone, netstat empty), mark the question OPEN/deferred, and cross-verify with other observers (c9: explorer + outlaw both hit 11/11 ConnectionRefused — agreement strengthens the absence claim; disagreement would be a discrepancy to resolve). The brute-force window question carries over to the next cycle.
- **Phantom redirect in CommandLine = mis-launched twin.** A process cmdline containing `2> C:\...\file.err.log` whose target file does NOT exist means the redirect was passed as a literal argv fragment (launcher used shell=False / args list). The "twin" still binds the port via Windows SO_REUSEADDR — it's a duplicate service, not a logger. Verify redirect targets named in wmic CommandLine actually exist; absence is a real hygiene finding.
- **Twin launchers**: same `.py` under two interpreters (hermes-venv python + uv cpython) — one binds the port, the twin idles. Flag as hygiene: a restart could bind the wrong twin. Detect via `wmic ... CommandLine` compare, not `tasklist` names.
- **Secret values must not reach artifacts**: never tee a probe printing full values; leak-grep the report and scripts before finishing.
- **"Dormant" ≠ "fixed"**: a risk script present but not running (e.g. watch daemon carrying a legacy credential in its restart env) stays a real finding — report blast radius + the fix, don't just note it's not running.
- **zsh guest login shell trips equals-expansion.** Kali guest login shell is zsh: a remote command containing `echo ===` fails with `zsh:1: == not found` and can abort the whole `-c` chain (output truncated, rc=1). Use `echo '---'` or other safe separators in all remote commands.
- **SSH credential resolution: the username IS the "kali/painbaba" search.** Neither .env contains the strings 'kali' or 'painbaba' (key or value) — grep'ing is a dead end. The Kali SSH login is `painbaba` + Hermes `.env` `SUDO_PASSWORD` value (loaded in-process, `allow_agent=False`). - **Crash-queue deconvolution + triage verdict.** Legacy counts like "51 crashes" are raw `find -name '*crash*'` counts across depths and conflate: distinct crash inputs (the real queue) + wrapper `.stdout/.stderr` sidecars from `run_fuzz_*` replay scripts + corpus copies + fuzzer `crash-<sha1>` units. Triage = replay EACH distinct input against the current ASAN harness with a timeout; `RC=0 / LLVMFuzzerTestOneInput returned 0` for all → **queue is stale** (inputs predate harness rebuilds; hand-curated 9–21B headers are usually not real repros). - **`pgrep -af <pattern>` self-matches its own wrapper** (c18 aborted a seed on this). Run via SSH, `pgrep -af libFuzzer` matches the remote `zsh -c 'pgrep -af libFuzzer …'` wrapper itself (its cmdline contains the pattern) → false "STALE PROCS PRESENT", abort, or a bogus proc count. Fix: the **bracket trick** — `pgrep -af '[f]uzz_avc_asan|[f]uzz_hevc_asan'` (the wrapper's literal `[f]uzz…` text does not match the regex `[f]uzz`). Use `pgrep -cf '[f]uzz_(avc|hevc|jpeg)'` for counts, and cross-check with `ps -eo pid,etime,comm,args` — the two must agree (a one-off count of 5 vs 4 was a fork artifact). The same self-match applies to `grep`-based process checks; filter the wrapper line (`grep -v 'zsh -c'`) or use the bracket trick everywhere.
- **Don't `from cycleN_kali_recon import …` for a follow-up check** (c18). Expedition scripts execute their mission at MODULE LEVEL — importing any function re-runs the whole script (re-probing, re-seeding, possibly re-launching). The c18 re-import re-ran the script against the just-seeded VM; only the stale-proc guard prevented a double-seed. For a post-script verification pass, copy the 6-line ssh helper INLINE into a standalone snippet (never import), or structure probe scripts with `if __name__ == "__main__":` around the mission block.
